Dan Shipper 用 Vibe Coding 做了个文档编辑器叫 Proof。上线当天 4000 多人注册，然后服务器就崩了。

凌晨四点他坐在电脑前，看着 Codex 一遍一遍尝试修复他自己都看不懂的代码。

后来写了篇文章，标题翻译过来就是：当你的 Vibe Coding 应用爆火了——然后挂了。

这事在硅谷炸了锅，紧接着，Val Town 创始人 Steve Krouse 在 Hacker News 上发了一篇 350 分的长文，标题更直接：**代码已死？想多了。**

两篇文章说的是同一个问题：Vibe Coding 到底能走多远？

![[cb61dcd4bc936e66452b2eb787916dc0_MD5.jpg]]

## 先说 Dan Shipper 踩的那个坑

Dan Shipper 不是什么技术小白，他是 Every 的 CEO，写了好几年 AI 编程专栏。但做 Proof 这个项目，他从头到尾全程 Vibe Coding，用嘴告诉 AI 要什么，AI 生成代码，他看效果验收。

效率确实惊人：

- 10 天时间，从零做出一个能用的协作文档编辑器
- 代码仓库 1600 次提交、600 多个 PR、14 万行代码
- 全职开发者一年的提交中位数是 417 次，他 10 天超了人家一年

然后问题来了，4000 用户涌进来，应用开始间歇性崩溃，Dan 自己压根不理解底层代码，只能继续让 AI 去修。

AI 修得动吗？修得动，但修得慢——因为问题往往埋在他从未看过的抽象层里。

他的总结是一句很实在的话：**能用 Vibe Coding 写出来的东西，也能用 Vibe Coding 修好。但不一定修得快。**

## Steve Krouse 的观点

Steve Krouse 是 Val Town 的创始人，Val Town 是一个在线编程平台，用户直接在浏览器里写代码、部署服务，他本人就是"让编程更简单"这条路上走最远的人之一。

他的文章从一个哲学家的话开始：

> **“**"一切事物的模糊程度，远超你意识到的——直到你试图把它变精确。" —— 伯特兰·罗素

Vibe Coding 的核心体验是：你用自然语言描述需求，AI 把它变成代码。你看效果，觉得不对就再说一句"把按钮往左移一点"、"颜色换成蓝的"，整个过程你始终在"感觉"的层面操作，不碰具体实现。

Steve 说，这个过程会给你制造一种幻觉：**你的"感觉"就是精确的规格说明。**

实际上差远了。

## "实时协作"四个字背后的深坑

Dan Shipper 的 Proof 要做实时协作编辑。"实时协作"听上去是个很清楚的需求，我们每天都在用 Google Docs 和 Notion，好像很简单对吧？

Steve Krouse 说，他十年前也试过给产品加协作编辑功能，结果是"一场意想不到的复杂度噩梦"。

最要命的是，他说**他已经不记得到底难在哪了**。复杂度就是这么个东西，它不是一个大 boss，而是无数个你想都想不到的小怪。

他举了个经典的例子：Slack 决定什么时候给你发通知的流程图。那张图密密麻麻，光看就头疼。但用自然语言描述的话，"发通知"好像就三个字的事。

这就是 Vibe Coding 的陷阱所在：**自然语言天生就是模糊的，而代码必须精确。**中间的鸿沟不会因为 AI 变强就消失，只是被暂时遮住了。

![[91330b0e327c93556254f8bf741a6ac8_MD5.jpg]]

## 抽象：对抗复杂度的真正武器

Steve 没有停在"Vibe Coding 不行"这个结论上。他接着聊了一个更有意思的话题：抽象。

人脑一次只能处理 7 个左右的信息，想处理更多怎么办？把一堆东西压缩成一个概念，这就是抽象。

React 是对 DOM 操作的抽象，TailwindCSS 是对 CSS 的抽象，协作编辑库是对冲突解决算法的抽象。

Dijkstra 说过一句话：

> **“**"抽象的目的不是变得模糊，而是创造一个新的语义层，在这个层面上你可以做到绝对精确。"

编程里最有价值的活，不是敲代码本身，而是**设计好的抽象来驾驭复杂度**。这个能力，AI 目前还差得远。

## 代码没有死，甚至还没到最好的时候

整篇文章里最让人拍大腿的一段，是 Steve 对"代码已死"论调的反击：

他说，现在 99% 的人都在说代码要死了，连播客主持人 Sam Harris 都在自信地聊这个话题。

Steve 的反应是：**这跟说印刷术发明了，讲故事就死了一样荒谬。**

他做了一个很妙的类比：为什么没有人在聊"Vibe Writing"？

没人觉得 ChatGPT 会取代优秀的小说家和记者，大家心里都清楚那是扯淡。但同样的道理放到代码上，怎么突然这么多人就信了？

原因在于代码有一层"魔法"的错觉——能跑起来的程序给人一种"完成了"的感觉；但写作不会，一段语法正确但内容空洞的文字，谁都看得出来是垃圾。

代码也一样，AI 写的代码能跑，但"能跑"和"写得好"之间，差的不是一点半点。

## Vibe Coding 的边界到底在哪

综合 Dan 和 Steve 的经验，界线其实挺清楚的：

**适合 Vibe Coding 的：**

- 原型验证、MVP、内部工具
- 个人项目、一次性脚本
- 界面调整、样式修改这类不涉及深层逻辑的活
- 快速试错，验证一个想法能不能走通

**不适合纯 Vibe Coding 的：**

- 需要承受真实流量的生产环境
- 实时协作、并发处理、状态同步这类本质复杂的问题
- 你完全看不懂生成代码的项目——出了问题你连排查方向都没有
- 需要长期维护的项目——Vibe 出来的代码，三个月后你（和 AI）可能都读不懂

Dan 自己的总结很到位：Vibe Coding 不是不能用，关键是得知道它的天花板在哪，能 Vibe 出来的东西确实也能 Vibe 修好，但修的速度跟懂代码的人比，差距很明显。

![[89d3c925f49b372f607a901f911a8d81_MD5.jpg]]

## 写在最后

Vibe Coding 是真的强，Dan Shipper 10 天做出 14 万行代码的产品，这在两年前不可想象。

但"能做出来"和"能撑住"是两回事，代码不只是让程序跑起来那么简单，它是一种精确表达思维的方式，是人类驾驭复杂度的工具，这个层面的价值，不会因为 AI 能生成代码就消失。

Steve Krouse 说了一句我特别认同的话：等真正的 AGI 来了，我们第一件事不是用它来生产更多垃圾代码，而是用它来创造更好的抽象，帮我们理解和掌控更高层次的复杂度。

所以结论不是"别用 Vibe Coding"，而是：**用它来走得更快，但别忘了你最终需要懂你在造什么。**
